# Monitoring notes

This page covers the monitoring stack in `monitoring/`: what it watches, how alerts are routed, how to deploy it, and how to test it. The plain-language version is in the README.

## What runs

`monitoring/docker-compose.yml` starts six containers, each with a pinned version:

| Service | Image | Job |
|---|---|---|
| `prometheus` | prom/prometheus v2.55.1 | Scrapes every 30 s, keeps 30 days, evaluates the alert rules |
| `alertmanager` | prom/alertmanager v0.27.0 | Groups alerts, applies the routing and repeat rules, sends them on |
| `node-exporter` | prom/node-exporter v1.8.2 | Host CPU, memory, load, disks, and the backup textfile |
| `blackbox-exporter` | prom/blackbox-exporter v0.25.0 | Probes the LifeOS demo over HTTPS and reads its certificate expiry |
| `grafana` | grafana/grafana 11.3.0 | The `Home server` dashboard, with the Prometheus data source provisioned from files |
| `alert-sink` | python 3.12 (stand-in) | Prints each alert it receives. Replace it with a real notifier |

Ports are bound to `127.0.0.1`. To open Grafana from your laptop, use an SSH tunnel:
`ssh -L 3000:127.0.0.1:3000 admin@home-server`.

## Setup

1. Copy `monitoring/.env.example` to `monitoring/.env` and set `GRAFANA_ADMIN_PASSWORD`. The file is ignored by Git.
2. Set `BACKUP_TEXTFILE_DIR` to the host folder that holds `home-ops-backup.prom`. The default is `monitoring/textfile`.
3. Start the stack: `cd monitoring && docker compose up -d --wait`.
4. Check it: `PROM_URL=http://127.0.0.1:9090 GRAFANA_URL=http://127.0.0.1:3000 monitoring/scripts/check_targets.sh` (run from the repository root).

To deploy with Ansible instead, put the password in the vault (`vault_grafana_admin_password`, at least 12 characters) and run `cd ansible && ansible-playbook -i inventory/hosts.yml monitoring.yml --check --diff`, then without `--check`.

## The backup timestamp

The backup CronJob in `k8s/charts/home-ops/templates/backup.yaml` runs `gzip -t` on each dump. Only if that passes does it write `home-ops-backup.prom` into `/backups/textfile/`, containing `home_ops_backup_last_success_timestamp_seconds{database="..."}` with the current Unix time.

The backups volume is a Kubernetes volume, so its textfile folder lives on the host under the storage path your cluster uses. Copy or point that folder at `BACKUP_TEXTFILE_DIR`. Until the folder is set, `BackupTimestampMissing` fires after an hour, which is the intended signal.

## Alerts

Rules are in `monitoring/prometheus/rules/home-server.yml`. Every alert has a `for:` duration so a brief blip does not page, and a runbook in `monitoring/runbooks/` named after the alert.

| Alert | Fires when | For | Severity |
|---|---|---|---|
| `LifeOSDemoDown` | the demo does not answer the probe | 10 min | critical |
| `LifeOSHealthDown` | `/healthz` does not return 2xx | 10 min | critical |
| `ServiceDown` | Prometheus cannot scrape node, blackbox, alertmanager or prometheus | 5 min | critical |
| `TLSCertificateExpiresSoon` | the LifeOS certificate has under 14 days left | 1 h | warning |
| `TLSCertificateExpiresVerySoon` | the LifeOS certificate has under 3 days left | 1 h | critical |
| `DiskWillFillWithin24h` | the 6-hour trend says full within 24 h **and** less than 25% free | 30 min | warning |
| `DiskAlmostFull` | less than 10% free | 10 min | critical |
| `BackupStale` | the last verified backup is over 26 hours old | 10 min | critical |
| `BackupTimestampMissing` | no backup timestamp for an hour | 1 h | warning |

The disk trend rule needs both conditions. A trend alone fires whenever a disk grows at night, and the free-space condition keeps that quiet while there is plenty of room. Routing is in `monitoring/alertmanager/alertmanager.yml`: critical alerts repeat hourly, warnings every four hours, and warnings for an instance are hidden while `ServiceDown` is firing for it.

## Dashboard

`monitoring/grafana/dashboards/home-server.json` is generated by `make_dashboard.py`. Edit the script, run it, and commit both. The test `monitoring/tests/test_monitoring_config.py` fails if they differ. The dashboard has three sections: availability (the LifeOS probes, targets up, certificate days left), performance (CPU, load, memory, probe timing) and disk capacity (used percentage, time to full, hours since the last backup, active alerts).

## Recovery playbooks

- `ansible/runbooks/restart-service.yml` restarts one systemd unit and waits for a health URL.
- `ansible/runbooks/restore-backup.yml` checks the `.sha256` file and `gzip -t`, stops a service, runs a restore command you give it, and starts the service again. Point the restore command at a scratch database first.

## Tests

| Check | Where | What it proves |
|---|---|---|
| `python -m pytest -q monitoring/tests` | CI `rules` job | Every alert has a runbook and a promtool case, the job names exist, images are pinned, the dashboard is current |
| `promtool check config` and `promtool check rules` | CI `rules` job | Syntax and schema of the Prometheus files |
| `promtool test rules monitoring/prometheus/tests/alerts_test.yml` | CI `rules` job | Each alert fires at the right time and stays quiet for short blips, a 5-minute exporter stop, a 2-minute LifeOS blip, a disk trend with plenty of free space, and a 27-hour-old backup |
| `amtool check-config` | CI `rules` job | Alertmanager routing and receivers parse |
| `monitoring/scripts/check_targets.sh` | CI `stack` job | The compose stack starts, every scrape target is `up`, the textfile metric arrives, Grafana reports its database as ok |
| `ansible-lint monitoring.yml runbooks/` | CI `ansible` job | The playbooks follow the lint rules, and each one passes a syntax check |

Run the promtool checks locally with a Prometheus binary: `cd monitoring/prometheus && promtool test rules tests/alerts_test.yml`.

## Limits

- The notifier is a stand-in. Alerts are printed by `alert-sink` until you point `alertmanager.yml` at email, ntfy or another receiver.
- The LifeOS health path `/healthz` is an assumption. Change it in `prometheus.yml` and in the alert text if the app uses a different path.
- The stack watches the host and the probes. It does not replace the backups' own checks, and a stopped Prometheus is not reported by Prometheus. An external watchdog is the next step if that matters.
